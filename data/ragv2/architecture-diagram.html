The whole approach, end to end

Two independent entry points — a document being uploaded, a question being asked — write into and read from the same three stores, then merge into one retrieval → correction → generation → verification pipeline. Color marks which phase a step belongs to; border style marks whether it costs an LLM call.

Sheet 01 — System context

Where RAG sits inside Darwin

The RAG pipeline isn't the assistant — it's one tool the supervisor agent reaches for, alongside camera control and voice, whenever a question needs the knowledge base rather than a live action.

Sheet 02 — Ingestion, offline per document

Parsing escalates only when it has to

Most files take the cheap, deterministic path. A document only reaches an LLM if the deterministic parser actually flags a problem it can name.

Sheet 03 — Retrieval & evidence grading, per query

The fork that decides whether the LLM ever sees the evidence

This is the mechanism behind most of this session's debugging: grading a passage almost never reaches the careful, LLM-graded judgment — a deterministic shortcut usually resolves it first, on retrieval score alone.

Sheet 04 — Generation, verification & the correction loop

A state machine that can rewrite, retry, or give up

Weak evidence triggers a rewrite-and-retry pass before generation ever runs; an unsupported answer triggers a second generation attempt, then a web search, before the system abstains.
